# i18n (TR/EN)

> URL-based TR/EN internationalization for `apps/web` via `next-intl`. Cross-cutting
> (TR default, EN at `/en/…`). The backend already had TR/EN locale files (`nestjs-i18n`); this wired
> the frontend.

## Overview

`apps/web` is TR/EN bilingual, URL-based: Turkish (default, no prefix) and English (`/en/…`).
`next-intl@^3.26.0` provides locale-aware routing, server + client translation hooks, and a
language switcher. Every API request sends `Accept-Language` so backend messages arrive in the
active locale. Static rendering / ISR stays **on** (no next-intl v4 needed) via two workarounds
(Turbopack alias + `[locale]`-owned `<html>`).

## Architecture (key decisions)

- **URL-based, `as-needed` prefix** — `locales: ["tr", "en"]`, `defaultLocale: "tr"`,
  `localePrefix: "as-needed"` (Turkish URL has no prefix, English is `/en/…`). `src/middleware.ts`
  (next-intl middleware; skips `_next`, `api`, static files).
- **Localized `pathnames` contract** — source folders and hrefs use English internal canonicals;
  `routing.ts` maps them to prefixes-free Turkish paths and `/en` English paths. Dynamic navigation
  uses `{pathname, params, query}`; canonical, sitemap, robots, and share URLs use `getPathname`.
  Global automatic alternate links are disabled until public content is genuinely translated.
- **Routing primitives in `src/i18n/navigation.ts`** — re-exports locale-aware `Link`, `useRouter`,
  `usePathname`, `redirect`, `getPathname` from next-intl. **Internal nav must use these**, not
  `next/link` / `next/navigation` (so locale prefix is automatic). Exception: `useSearchParams` still
  comes from `next/navigation` (next-intl doesn't override it).
- **`[locale]/layout.tsx` owns `<html>`/`<body>`** — awaited `params` (no dynamic read), so the
  render tree stays static. A separate `src/app/layout.tsx` was **removed** (it forced the whole
  tree dynamic). Fonts + `globals.css` + `NextIntlClientProvider` + `AuthProvider` +
  `BackgroundBlobs` live here.
- **Static render workarounds (ON without v4):**
  1. **Turbopack alias** — next-intl 3.26 plugin writes the `next-intl/config` alias to the wrong
     key (`experimental.turbo`); Next 16 reads `turbopack`. Set it manually:
     ```ts
     turbopack: { resolveAlias: { "next-intl/config": "./src/i18n/request.ts" } }
     ```
     (A harmless "Unrecognized key 'turbo'" warning remains — goes away in v4.)
  2. **`setRequestLocale(locale)` on every server page/layout** — otherwise the page falls to dynamic
     `ƒ`. `(app)` layout is client → each `(app)` page takes locale from awaited `params`;
     `(auth)` layout is server → covers 5 auth pages at one point.
- **Locale validation** — `[locale]/layout.tsx` rejects invalid segments: `!routing.locales.includes(locale)`
  → `notFound()`. (`hasLocale` is not a public export in v3.26 — manual check; v4 brings it.)
- **API client locale** — `packages/api-client/src/http.ts` `ApiClientConfig` gained `getLocale?: () => string`;
  every request sends `Accept-Language`. Network error fallback is locale-aware. `auth-context.tsx`
  calls `configureApiClient({ getLocale: () => locale })` so the client updates on locale change.

## Tutorials / Guides

```tsx
// Client component
import { useTranslations } from "next-intl";
const t = useTranslations("panel");
// t('greeting', { name: user.name })

// Server component / page
import { getTranslations } from "next-intl/server";
const t = await getTranslations("panel");

// Internal navigation (locale-aware):
import { Link, useRouter, usePathname } from "@/i18n/navigation";
```

```bash
pnpm --filter @mentor/web dev

```

- **Adding a new string:** update **both** `messages/tr.json` and `messages/en.json` (14 namespaces,
  ~290 keys, kept in parity).
- **Adding a new `[locale]` server page/layout:** call `setRequestLocale(locale)` — else it goes dynamic `ƒ`.

## Directory structure

```
apps/web/
  messages/{tr,en}.json         # translation catalogs (root, not src/)
  src/
    middleware.ts               # next-intl middleware
    i18n/{routing,request,navigation}.ts
    app/[locale]/
      layout.tsx                # root document: <html lang>/<body> + fonts + globals + providers
      (app)/                    # authenticated routes
      (auth)/                   # auth routes
      _components/              # landing components
      knowledge/                # public knowledge-center source route
```

## Gotchas / Known issues

- **`messages/` is at `apps/web/` root** (not inside `src/`).
- **Import `Link` from `@/i18n/navigation`** — not `next/link` (else locale prefix is lost).
- **`useSearchParams` still from `next/navigation`** (next-intl doesn't override it).
- **No separate `src/app/layout.tsx`** — `[locale]/layout.tsx` owns `<html lang={locale}>`/`<body>`.
- **`hasLocale` is not public in next-intl v3.26** — manual `routing.locales.includes()` check; v4
  exports it.
- **Harmless "Unrecognized key 'turbo'" warning** remains (plugin writes the old key; v4 cleans it).
- **Backend already had TR/EN** (`nestjs-i18n`) — frontend `Accept-Language` makes messages arrive
  in the active locale automatically.
