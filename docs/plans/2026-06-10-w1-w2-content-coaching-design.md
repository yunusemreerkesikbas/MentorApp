## 1. Overview & scope

Two MVP tracks, developed in parallel under their exclusive ownership boundaries (`docs/workstreams.md §1`):

- **W1 — Content** → `apps/api/src/modules/content/**`, web `bilgi` + public SEO pages. Exam calendar (trusted, editorial), knowledge center (A-layer articles + pgvector column), exam/subject taxonomy + `net_rule` config. **Content is the system of record for all "official" / reference data.**
- **W2 — Coaching** → `apps/api/src/modules/coaching/**`, web app screens (`plan`, `analiz`, session UI, mood prompt). Daily loop (plan tasks, calm countdown, Pomodoro sessions, streak), deneme (mock-exam) analysis, mood check-in. **Coaching is the system of record for all per-user behavioral data.**

**Strategy (locked): thin vertical slice per feature.** The full W1+W2 feature set is designed now, built incrementally one shippable slice at a time. Each slice is end-to-end (schema → migration → repo → service → controller → api-client → web screen → devnote).

**Locked slice order:**

| # | Slice | Track | Unlocks |
|---|---|---|---|
| 1 | **Exam Calendar** | W1-a | Authoritative countdown date (exam selection = existing W0 `users.examType`) |
| 2 | **Daily loop** (plan tasks · countdown · sessions · streak) | W2-a | Core habit surface |
| 3 | **Deneme analysis** (net + trend) | W2-b | Needs `net_rule` + subject taxonomy from W1 |
| 4 | **Knowledge center** (articles + pgvector + SEO) | W1-b | RAG source for W3 (AI) |
| 5 | **Mood check-in** (rule-based) | W2-c | Future low-mood signal to coach (Phase 2) |

Deferred to a later slice (explicitly out of scope here): **Ghost** and **vision board** (both W2).

**Current codebase state (verified):**
- Only `identity` module exists under `apps/api/src/modules/`. **`content` and `coaching` modules do not exist yet** — both are greenfield (folders are reserved only by `modules/README.md`, not on disk).
- `database/schema.ts` currently holds `jobs` + W0 identity tables; it is **append-only** and shared (`docs/workstreams.md §2`).
- `vector` (pgvector) extension is **already enabled** in migration `apps/api/drizzle/0000_lean_the_santerians.sql` → the W1-b `embedding` column needs no extension migration.
- Web app screens (`panel/plan/analiz/bilgi/profil`) are placeholders (`components/coming-soon.tsx`); `(app)` is auth-guarded (`apps/web/src/app/(app)/layout.tsx`).

## 2. Guardrail alignment (AGENTS §4)

| Guardrail | Where it lands in this design |
|---|---|
| **#1 — Official info is never LLM-generated; critical facts render as data cards** | Exam dates and knowledge articles are **editorial seed only** (`ContentService.upsertExam/upsertEvent`, `info_articles` editorial rows). The `bilgi` exam-day view renders a **data card** (exam name, exact date, "Kaynak: ÖSYM ↗", "Son doğrulama: …") straight from `exam_events` columns — **no paraphrase, no LLM in the path**. Trust metadata (`source`, `source_url`, `verified_at`, `verified_by`) is mandatory on every event/article. |
| **#5 — AI→teacher trust line (raw confessions never reach coach)** | `mood_checkins` stores a 1–5 integer only — **no free-text note** (locked). Future low-mood handling produces a **signal/flag only**, never raw text, and is out of MVP scope. Mood messages are rule-based, never AI. |
| **#6 — KVKK / pgvector content-only** | `embedding vector` lives **only** on `info_articles` (content). **No behavioral table** (`plan_tasks`, `study_sessions`, `mock_exams`, `mood_checkins`, …) carries an embedding. Behavioral data stays in Postgres under RLS. No PII leaves to the LLM in this scope (embeddings are generated by W3 from public article text). |
| **#7 — org/exam-agnostic schema from day one** | `exams` carries a **nullable `org_id`** (global rows = `NULL`, org-scoped later). The product is exam-agnostic: per-exam behavior (`net_rule`, subject taxonomy, calendar) is **data/config in W1 content**, not a code "vertical". KPSS is just the first seed. All coaching tables are `user_id`-scoped and org-ready via the existing RLS pattern. |

## 3. Slice-by-slice design

Conventions used below (match the existing codebase):
- Drizzle sketches follow `database/schema.ts` patterns: `uuid` PK `default(sql\`gen_random_uuid()\`)`, `timestamp(..., { withTimezone: true })`, `snake_case` columns / `camelCase` TS fields, indexes via the `(t) => [...]` array form, `set_updated_at()` trigger added in the migration.
- Tables are appended to `database/schema.ts` in **clearly-commented per-track blocks** (`/* ===== W1 · content ===== */`, `/* ===== W2 · coaching ===== */`) — append-only shared surface (`docs/workstreams.md §2`).
- Module layout follows `identity`: `presentation/` (controller + `*.dto.ts`), `application/` (service), `infrastructure/` (`*.repository.ts`), `domain/` (constants/pure logic). Pragmatic Clean: these CRUD-ish modules use `controller + service + repository`; the only "critical domain" pure logic is **net computation** (W2-b) → keep it framework-free in `coaching/domain/net.ts`.
- Validation schemas appended to `@mentor/validation` (append-only, `packages/validation/src/`), shared FE+BE; DTOs via `createZodDto(...)` exactly like `identity/presentation/auth.dto.ts`.
- All lists paginated with `paginationQuerySchema`; all user-facing copy localized from the backend (`message` + `code`); FE never recomputes business values.

### Slice 1 — Exam Calendar (W1-a)

**Data model** (`content` block in `schema.ts`):

```ts
/* ===================== W1 · content ===================== */

export const exams = pgTable(
  "exams",
  {
    id: uuid("id").primaryKey().default(sql`gen_random_uuid()`),
    slug: text("slug").notNull(),                       // e.g. "kpss-lisans-2026"
    name: text("name").notNull(),
    type: text("type").notNull(),                        // LISANS | ONLISANS | ORTAOGRETIM
    netRule: jsonb("net_rule").notNull(),                // e.g. { kind: "PENALTY", divisor: 4 }
    orgId: uuid("org_id").references(() => organizations.id), // nullable → global row (§4 #7)
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [uniqueIndex("exams_slug_unique_idx").on(t.slug)],
);

export const examEvents = pgTable(
  "exam_events",
  {
    id: uuid("id").primaryKey().default(sql`gen_random_uuid()`),
    examId: uuid("exam_id").notNull().references(() => exams.id),
    type: text("type").notNull(),                        // EXAM_DATE (first); APPLICATION/PREFERENCE later
    eventAt: timestamp("event_at", { withTimezone: true }).notNull(),
    source: text("source").notNull(),                    // "ÖSYM"
    sourceUrl: text("source_url").notNull(),             // trust metadata (§4 #1)
    verifiedAt: timestamp("verified_at", { withTimezone: true }).notNull(),
    verifiedBy: text("verified_by").notNull(),           // editor id/handle
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [index("exam_events_exam_type_idx").on(t.examId, t.type)],
);
```

`net_rule` is stored as `jsonb` so a new exam (e.g. YKS) is pure data. KPSS seed: `{ kind: "PENALTY", divisor: 4 }`.

**Seed & admin-readiness:** editorial data is loaded from a versioned JSON seed (`apps/api/src/modules/content/seed/exams.seed.json`) routed through `ContentService.upsertExam()` / `upsertEvent()` (idempotent upsert on `slug` / (`exam_id`,`type`)). W6 admin later calls the **same service methods** for CRUD → zero schema change.

**Exam-type → current exam selection rule (LOCKED).** The countdown's exam is resolved from the user's `users.examType` (`LISANS | ONLISANS | ORTAOGRETIM`) → the matching `content.exams.type`. When multiple exams share a type, pick the one with the **nearest upcoming `EXAM_DATE` event** (default rule). Optionally, editorial can mark the active exam with an `is_current` boolean on `exams` (`isCurrent: boolean("is_current").notNull().default(false)`) for an explicit override; document whichever is used. This keeps "which exam" out of coaching storage entirely.

**API** (`/v1/content/*`, kebab-case, paginated):
- `GET /v1/content/exams` → exam list for onboarding (`@Public` — reference data). `Paginated<ExamSummary>`.
- `GET /v1/content/exams/:slug/calendar` → data-card payload by slug: `{ exam: { slug, name, type }, events: [{ type, eventAt, source, sourceUrl, verifiedAt }] }`. Backend returns ready-to-render values (no FE date math beyond formatting).
- `GET /v1/content/exams/by-type/:type/calendar` → **authoritative countdown source**: resolves the current exam for an exam type (selection rule above) and returns the same data-card payload (used by coaching for the countdown).

**Services / ports:** `ContentService` (public read methods `getExam(slug)`, `listExams()`, `getCalendar(slug)`, **`getExamByType(examType)`**, **`getExamCalendar(examType)`**; write methods `upsertExam`, `upsertEvent`). These public reads are the **cross-track contract** consumed by coaching (see §4) — exposed via the module's exported provider, never via table access.

**Web (`apps/web/src/app/...`):**
- Authenticated `(app)/bilgi` → exam-day **data card** (calm, no alarm-red — DESIGN §9 / frontend standard tone): `@mentor/ui` `Card` + `Chip` for "Kaynak: ÖSYM ↗", secondary-text for "Son doğrulama: …". Server Component fetching via `@mentor/api-client`.
- Exam list feeds the **W0 onboarding step** (exam-type selection on `users.examType`).

**Cross-track note (no coaching table here):** "Which exam" is **not** re-stored by coaching. The chosen exam type already lives on the identity `users.examType` column (set at W0 onboarding). Coaching reads it from the **current user's own record via the identity user service / `RequestContext`** — never by querying the `users` table from a coaching repository (workstreams §3 cross-module rule). The exam's authoritative dates come from W1 via `ContentService.getExamByType` / `getExamCalendar` (soft-ref by exam type; no FK, no cross-module JOIN). There is intentionally **no `study_profiles` table** (it would duplicate identity data — YAGNI). If coaching-specific profile fields are genuinely needed later, a `study_profiles` table can be introduced at that point.

### Slice 2 — Daily loop (W2-a)

**Data model** (coaching block — first coaching tables; open the `/* ===== W2 · coaching ===== */` block here):

```ts
/* ===================== W2 · coaching ===================== */

export const planTasks = pgTable(
  "plan_tasks",
  {
    id: uuid("id").primaryKey().default(sql`gen_random_uuid()`),
    userId: uuid("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
    taskDate: date("task_date").notNull(),
    title: text("title").notNull(),
    subject: text("subject"),                            // nullable SOFT ref → content subject slug
    status: text("status").notNull().default("PENDING"), // PENDING | DONE
    sortOrder: integer("sort_order").notNull().default(0),
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [index("plan_tasks_user_date_idx").on(t.userId, t.taskDate)],
);

export const studySessions = pgTable(
  "study_sessions",
  {
    id: uuid("id").primaryKey().default(sql`gen_random_uuid()`),
    userId: uuid("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
    startedAt: timestamp("started_at", { withTimezone: true }).notNull(),
    endedAt: timestamp("ended_at", { withTimezone: true }),
    preset: text("preset").notNull(),                    // "25_5" | "50_10"
    actualFocusSeconds: integer("actual_focus_seconds").notNull().default(0),
    subject: text("subject"),                            // nullable SOFT ref
    status: text("status").notNull().default("COMPLETED"), // COMPLETED | ABANDONED
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [index("study_sessions_user_started_idx").on(t.userId, t.startedAt)],
);

export const dailyActivity = pgTable(
  "daily_activity",
  {
    id: uuid("id").primaryKey().default(sql`gen_random_uuid()`),
    userId: uuid("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
    activityDate: date("activity_date").notNull(),
    hasSession: boolean("has_session").notNull().default(false),
    tasksDone: integer("tasks_done").notNull().default(0),
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [uniqueIndex("daily_activity_user_date_unique_idx").on(t.userId, t.activityDate)],
);

export const streakState = pgTable(
  "streak_state",
  {
    id: uuid("id").primaryKey().default(sql`gen_random_uuid()`),
    userId: uuid("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
    currentStreak: integer("current_streak").notNull().default(0),
    longestStreak: integer("longest_streak").notNull().default(0),
    freezeTokens: integer("freeze_tokens").notNull().default(2),
    lastActiveDate: date("last_active_date"),
    freezeMonth: text("freeze_month"),                   // "YYYY-MM" — for monthly token reset
    createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp("updated_at", { withTimezone: true }).notNull().defaultNow(),
  },
  (t) => [uniqueIndex("streak_state_user_unique_idx").on(t.userId)],
);
```

Requires importing `boolean` into the schema import list (currently not imported).

**Business rules (backend-only; constants in `coaching/domain/streak.ts`, not magic numbers):**
- **Streak day** = ≥1 `COMPLETED` session **OR** ≥1 `DONE` task on that date (`daily_activity` row).
- **Anti-shaming (§0 tone):** `freezeTokens` default 2/month, auto-consumed for a **single** missed day; otherwise **soft reset** with encouraging copy (localized message from backend), never shaming. Monthly reset keyed on `freezeMonth`.
- **Computation:** rule-based, **read-time derived** in MVP (compute on read from `daily_activity`/`streak_state`). Path to W5: a `coaching.recompute-streak` job via `JobQueuePort` (nightly) — designed for, not built now.
- **Countdown:** the exam type comes from the current user's `users.examType` (read via the identity user service / `RequestContext`, not a coaching query against `users`); the authoritative `EXAM_DATE` is fetched via `ContentService.getExamCalendar(examType)` (content calendar = sourced/verified, guardrail #1). **No new table.** Calm framing (not alarm-red). **`users.examDate` is NOT a source** for the countdown and must not be used as a silent fallback (see §6).

**API** (`/v1/coaching/*`):
- `GET/POST/PATCH /v1/plan-tasks` (list by `?date=`, create, update status/sort) — paginated list.
- `POST /v1/study-sessions` (start) · `PATCH /v1/study-sessions/:id` (complete/abandon with `actualFocusSeconds`).
- `GET /v1/coaching/today` → composite "daily loop" payload: today's tasks, streak summary, countdown (days to exam), session presets. One server round-trip for the panel (no FE waterfall — frontend standard).
- Note: the api.md catalog lists planned base paths `/v1/plans`, `/v1/study-sessions`, `/v1/mock-exams`, `/v1/check-ins`; align final names and update the catalog row when shipped.

**Services/ports:** `PlanService`, `SessionService`, `StreakService` (+ `domain/streak.ts` pure rules). On session-complete / task-done, the service upserts `daily_activity` and updates `streak_state` in the same tx.

**Web:** `(app)/plan` (today's tasks CRUD + sort, `@mentor/ui` `Card`/`Button`/`Chip`, `ProgressBar` for completion), calm **Countdown** widget on `(app)/panel`, session/Pomodoro timer UI (preset 25/5 or 50/10). **Open item:** there is no `seans` route in `app-nav.tsx`; DESIGN §9 mentions a "central study action". See §6 for the session-UI placement question.

### Slice 3 — Deneme analysis (W2-b)

**Data model** (coaching block):

```ts
export const mockExams = pgTable(

  {
    id: uuid("id").primaryKey().default(sql`gen_random_uuid()`),
    userId: uuid("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),

export const mockExamSubjects = pgTable(
  "mock_exam_subjects",
  {
    id: uuid("id").primaryKey().default(sql`gen_random_uuid()`),
    mockExamId: uuid("mock_exam_id").notNull().references(() => mockExams.id, { onDelete: "cascade" }),
    subjectRef: text("subject_ref").notNull(),           // SOFT ref → content subject slug
    correct: integer("correct").notNull(),
    wrong: integer("wrong").notNull(),
    blank: integer("blank").notNull(),
    net: numeric("net", { precision: 6, scale: 2 }).notNull(), // derived, stored

  },
  (t) => [index("mock_exam_subjects_mock_idx").on(t.mockExamId)],

```

Requires importing `numeric` into the schema import list.

**Net computation (critical domain — backend only):** input is per-subject D/Y/Boş. Net is computed from the exam's `net_rule` fetched via `ContentService.getExam(examId)`. KPSS: `net = correct − wrong/4`. The divisor is **not** a magic number — it comes from `net_rule.divisor`; the pure function lives in `coaching/domain/net.ts` and is the single source (FE never recomputes — engineering-principles §4). Money/score transported as string per api.md (`numeric`).

**API:**
- `POST /v1/mock-exams` → body: `{ examId, takenAt, subjects: [{ subjectRef, correct, wrong, blank }] }`; backend computes per-subject net + `totalNet`, persists, returns the computed record.
- `GET /v1/mock-exams` (paginated) · `GET /v1/mock-exams/:id`.
- `GET /v1/coaching/analysis` → **personal** net trend time series + per-subject strong/weak breakdown (computed server-side). **Guardrail: no ranking / no leaderboard — personal trend only** (§0).

**Web:** `(app)/analiz` — entry form (per-subject D/Y/Boş → live net shown from the **POST response**, not FE math), net trend chart, per-subject strong/weak. **Open item:** `@mentor/ui` has no chart primitive (only `ProgressBar`); see §6.

## 4. Cross-track contracts & seams

1. **`ContentService` public reads (W1 → W2), soft-ref only.** "Which exam" the user is preparing for is **owned by identity** (`users.examType`, set at W0 onboarding) — coaching does **not** re-store it and there is **no `study_profiles` table**. Coaching reads the type from the current user's own record via the **identity user service / `RequestContext`** (never a coaching query against `users` — workstreams §3). The exam's authoritative dates come from W1 via **`ContentService.getExamByType(examType)` / `getExamCalendar(examType)`** (soft-ref by exam type; no FK, no cross-module JOIN). Coaching's other soft references (`plan_tasks.subject`, `mock_exam_subjects.subject_ref`) resolve via the exported `ContentService` (`getExam`, `getCalendar`, `getExamByType`, `getExamCalendar`, `listExamSubjects`) with **no hard FK and no cross-module table access** (backend standard "no direct cross-module table/repo access"; AGENTS §2). In MVP both modules run in one process → consume the provider directly; the boundary is the public method signature, not the table.
2. **`net_rule` + subject taxonomy live in content/config.** Net divisor and per-exam subject list are data owned by W1; W2's net computation reads `net_rule` via `ContentService` and uses `coaching/domain/net.ts` for the pure math. Single source of truth → exam-agnostic (§4 #7).
3. **`ArticlePublished` domain event (W1 → W3).** Embedding generation is decoupled: W1 emits, W3 consumes (`JobQueuePort` → `ai.embed-article`). W1 ships the `embedding` column + event with **zero OpenAI dependency**.
4. **`JobQueuePort` (W1/W2 → W5).** Streak nightly recompute and article embedding are **latency-tolerant** and belong on the queue (`shared/ports/job-queue.port.ts`). **Only W5 implements the runner** (`docs/workstreams.md §1`). See §6 for the "no adapter bound yet" gap.
5. **Append-only shared surfaces** (`docs/workstreams.md §2`): `database/schema.ts` (per-track commented blocks), `drizzle/` (sequential migrations, forward-only), `app.module.ts` (one alphabetical import line per module: `ContentModule`, `CoachingModule`), `@mentor/{validation,types}` (only genuinely shared contracts; feature types stay in-module), `docs/standards/api.md` service-catalog row (flip `content`/`coaching` status when shipped), `docs/features/{content,coaching}.md` (append a dated timeline entry per shipped slice).

## 6. Open technical questions / risks (discovered in code)

1. **`JobQueuePort` has no bound adapter yet.** `JOB_QUEUE_PORT` is defined but no provider binds it (W5 owns the runner; the `jobs` table exists). The streak nightly recompute (W2) and embedding enqueue (W1/W3) reference the port but **cannot run end-to-end until W5 lands**. *Mitigation:* MVP streak is **read-time derived** (no queue needed); W1's embedding is enqueued by **W3**, not W1. Confirm: do we ship a trivial no-op/stub `JobQueuePort` provider so modules can inject it before W5? (Recommend: W5 ships the binding; until then neither W1 nor W2 must hard-depend on enqueue.)
2. **Domain events are not wired.** `@nestjs/event-emitter` (`EventEmitterModule`) is **not imported in `app.module.ts`**, though docs assume NestJS `EventEmitter` for domain events. W1-b's `ArticlePublished` needs it. *Decision needed:* W1 adds `EventEmitterModule.forRoot()` to `app.module.ts` (a **shared/platform change** — coordinate per workstreams §2), or W1 enqueues directly via `JobQueuePort`. Recommend wiring `EventEmitterModule` (minimal, generic) since the architecture already specifies it.
3. **RLS policy for public reference tables.** Existing RLS pattern (migration 0001) is user/SERVICE/ADMIN scoped. The new **public reference tables** (`exams`, `exam_events`, `info_articles`, `subjects`, `exam_subjects`) are **read-by-anyone, write-by-editorial-only**. *Decision:* enable RLS with a read policy `USING (true)` + write policy restricted to `app.role IN ('SERVICE','ADMIN')`, OR leave them without RLS as non-tenant reference data. Recommend RLS-on with public read + service/admin write (consistent "double belt"). All **coaching** tables follow the existing per-user policy (`user_id = current_setting('app.user_id')` OR SERVICE/ADMIN).
4. **Migration ordering between W1 and W2 (parallel tracks, one `schema.ts`).** Next migration is `0002`. Both tracks append to the same `database/schema.ts` and the same sequential `drizzle/` folder; slices interleave (W1-a, W2-a, W2-b, W1-b, W2-c). *Risk:* migration-number / schema-block merge conflicts. *Mitigation:* generate a migration **only when a slice's schema is final** (forward-only), keep each track's tables in its own commented block, and serialize migration generation (coordinate the `0002…000N` numbers across the two tracks).
5. **Deprecate `users.examDate` (LOCKED decision — single source of truth).** Exam **selection** = `users.examType` (identity-owned); exam **date** (countdown) = authoritative from the content calendar via `ContentService.getExamCalendar(examType)` (guardrail #1: sourced/verified, rendered as a data card — never a user-entered free-form date). There is **no `study_profiles` table** (dropped — it duplicated identity data; YAGNI until coaching-specific profile fields actually exist). `users.examDate` is **effectively deprecated and ignored for countdown**; **do not silently fall back to it** (engineering-principles §2 — no silent fallback masking missing data). *Action:* remove the `users.examDate` column via a **coordinated W0 migration** (forward-only) — out of scope for these W1/W2 slices, so it stays on the table for now but is unused. Until then, coaching must read the date only from content.
6. **Public SEO route lives inside the auth-guarded group.** `(app)/layout.tsx` redirects anonymous users to `/giris`. Public `bilgi/[slug]` (slice 4) and possibly the public exam calendar **must be a separate, non-guarded route group** (e.g. a public `bilgi/` segment outside `(app)`, with its own layout). Decide the route structure so the authenticated `(app)/bilgi` view and the public SEO pages coexist (shared `AppNav` changes are coordinated).
7. **No chart primitive in `@mentor/ui`.** `analiz` net-trend needs a time-series chart; `@mentor/ui` only has `ProgressBar`. *Decision:* build a small token-compliant SVG/line chart in `@mentor/ui` (preferred — keeps DESIGN tokens, no bundle bloat) vs. add a charting dep (watch bundle size — frontend perf priority #2). Either way, FE only renders the **backend-computed** series.
8. **Loose OpenAPI/api-client types (carried gap from devnote 0010).** Zod DTOs aren't introspected into OpenAPI → generated client types are loose; FE casts via `@mentor/types`. New W1/W2 endpoints inherit this; add shared response types to `@mentor/types` and cast at the api-client boundary until the zod→OpenAPI enrichment lands.
9. **`profil` route ownership.** `(app)/profil` exists as a placeholder but isn't clearly assigned in `docs/workstreams.md`. Confirm owner before either track edits it (likely W0/W2). Out of scope for these slices.
